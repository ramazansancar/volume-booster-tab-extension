# Automating the AMO submission with the add-ons API

Plan only. Nothing in this document is implemented yet.

Today a release means: `pnpm run package`, then hand-upload `dist/firefox-mv2-<version>.zip` to addons.mozilla.org, paste the version notes and the reviewer note from [`amo-submission.md`](amo-submission.md), upload the source archive, and then — the part that actually hurts — paste a summary and a description for every language AMO offers, one at a time, through the language selector beside each field. [`store-descriptions.md`](store-descriptions.md) already holds all 68 of those translations, so the text exists; it is the transfer that is manual and error-prone.

The [addons.mozilla.org API v5](https://mozilla.github.io/addons-server/topics/api/index.html) can do all of it. This plan is how to get there.

---

## What the API can and cannot do

Worth settling first, because it decides how much of the release stays manual.

| Step                                        | API                                                             | Verdict                             |
| ------------------------------------------- | --------------------------------------------------------------- | ----------------------------------- |
| Upload the build, get it validated          | `POST /addons/upload/`, poll `GET /addons/upload/<uuid>/`       | Automatable                         |
| Create the new version                      | `POST /addons/addon/<id>/versions/`                             | Automatable                         |
| Version notes (`release_notes`)             | same call, or `PATCH .../versions/<id>/`                        | Automatable, per locale             |
| Reviewer note (`approval_notes`)            | same call                                                       | Automatable                         |
| Source archive                              | `source` file field, multipart, on the version call             | Automatable                         |
| Summary, description, per locale            | `PATCH /addons/addon/<id>/` with translated-field objects       | **Automatable — this is the prize** |
| Name, homepage, support URL, tags, category | same `PATCH`                                                    | Automatable                         |
| Screenshots and preview images              | No documented v5 endpoint                                       | **Stays manual**                    |
| Submitting for review / publishing          | Implicit — a listed version enters the review queue on creation | Automatable                         |

So the target is: everything except screenshots. Screenshots change rarely and `store-assets/` is already generated by `pnpm run screenshots`, so leaving them out costs little.

### Authentication

JWT per [RFC 7519](https://datatracker.ietf.org/doc/html/rfc7519), HS256, signed with the JWT secret, sent as `Authorization: JWT <token>`. Claims:

| Claim | Value                                                                   |
| ----- | ----------------------------------------------------------------------- |
| `iss` | the JWT issuer, e.g. `user:543210:23`                                   |
| `jti` | a fresh cryptographic nonce per request — `crypto.randomUUID()` is fine |
| `iat` | now, Unix seconds UTC                                                   |
| `exp` | **at most `iat + 300`** — AMO rejects anything longer than five minutes |

Two consequences the implementation must respect:

1. **A token cannot outlive a long upload.** Validation polling and a source upload can easily exceed five minutes, so sign a fresh token per request rather than once per run. Cheapest correct rule: mint the token inside the HTTP helper, never cache it.
2. **`jti` must not repeat.** Generate it per request, not per run.

No npm dependency is needed. HS256 is three base64url segments and one `crypto.createHmac('sha256', secret)` — about 15 lines, in keeping with a project that ships zero runtime dependencies and hand-rolls its own zip writer.

### Credentials

`JWT issuer` and `JWT secret`, already obtained from [the AMO API key page](https://addons.mozilla.org/en-US/developers/addon/api/key/) — the same page revokes and regenerates them, which is the first thing to do if either ever leaks. They are secrets in the strict sense: they authorise publishing under this account.

- Local: read from the environment, `AMO_JWT_ISSUER` and `AMO_JWT_SECRET`. `.env` is already in [`.gitignore`](../.gitignore), so a `.env` loaded by `node --env-file=.env` works without new tooling.
- CI: GitHub Actions repository secrets under the same names.
- Never a CLI argument — arguments land in shell history and in the process table.
- The script must refuse to run if either is missing, and must never print either one, including inside an error message echoing a failed request.

## The locale problem, which is the real work

This is where a naive implementation breaks, so it is worth being precise.

Three different locale vocabularies are in play:

1. **`public/_locales/`** — 55 directories, underscored: `pt_BR`, `zh_CN`, `es_419`. Chrome's i18n table. Interface strings only.
2. **[`store-descriptions.md`](store-descriptions.md) headings** — 68 tags, hyphenated: `pt-BR`, `zh-CN`, `es-419`. The union of what Opera, Chrome and AMO offer.
3. **AMO's own accepted list** — production sets `AMO_LANGUAGES = PROD_LANGUAGES` ([`src/olympia/conf/prod/settings.py`](https://github.com/mozilla/addons-server/blob/master/src/olympia/conf/prod/settings.py)), and `PROD_LANGUAGES` in [`src/olympia/core/languages.py`](https://github.com/mozilla/addons-server/blob/master/src/olympia/core/languages.py) is **44 locales** — far fewer than the ~150 in that file's full `ALL_LANGUAGES` table. Checked 2026-10-01:

   ```text
   cs de dsb el en-CA en-GB en-US es-AR es-CL es-ES es-MX fa fi fr fur fy-NL
   he hr hsb hu ia it ja ka kab ko nb-NO nl nn-NO pl pt-BR pt-PT ro ru sk sl
   sq sr sv-SE tr uk vi zh-CN zh-TW
   ```

The third is the one the API goes by, and it does not match the second. Worse, a translation in a locale outside it is **not rejected**: [`translations/fields.py`](https://github.com/mozilla/addons-server/blob/master/src/olympia/translations/fields.py) skips it with a bare `continue`, so the `PATCH` succeeds and the text is simply gone. A wrong count here does not fail loudly; it quietly publishes less than intended. Diffing the two:

The repo's 68 tags, taken from the live file, are:

```text
am ar bg bn ca cs da de dsb el en en-AU en-CA en-GB en-US es es-419 es-AR
es-CL es-MX et fa fi fil fr fur fy-NL gu he hi hr hsb hu ia id it ja ka kab
kn ko lt lv ml mr ms nl nn-NO no pl pt-BR pt-PT ro ru sk sl sq sr sv sw ta
te th tr uk vi zh-CN zh-TW
```

Four reach AMO under another name:

| Tag  | AMO locale                                                                    |
| ---- | ----------------------------------------------------------------------------- |
| `en` | `en-US` — AMO has no bare `en`, **and this file already has its own `en-US`** |
| `es` | `es-ES` — AMO has no bare `es`                                                |
| `no` | `nb-NO`                                                                       |
| `sv` | `sv-SE`                                                                       |

**23 have no AMO locale at all** and cannot be sent: `am ar bg bn ca da en-AU es-419 et fil gu hi id kn lt lv ml mr ms sw ta te th`. That includes `fil`: AMO's code for it, `tl`, exists in `ALL_LANGUAGES` but not in production. These translations stay useful for Chrome, Edge and Opera; AMO shows its `default_locale` (en-US) to those users.

The remaining 41 are identity mappings.

> [!WARNING]
> `en` and `en-US` both exist in this file and both want to become AMO's `en-US`.
> Whichever is applied second wins, so the map must resolve this explicitly rather
> than let ordering decide: send `en-US` from the `en-US` section and map `en` to
> `null`. The same collision does not arise for `es`/`es-ES` — there is no `es-ES`
> section — but the map should assert that no two source tags ever resolve to the
> same AMO locale, and fail loudly if they do.

So of 68 sections, 24 are dropped (`en` as a duplicate of `en-US`, and the 23 unsupported tags) and **44 reach AMO** — exactly AMO's production list, every one of its locales covered.

> [!IMPORTANT]
> The list above is a snapshot of `PROD_LANGUAGES` and can change. Because AMO drops unknown locales silently, the sender must report every tag it does not send rather than rely on the response. [extension-stores-api](https://github.com/ramazansancar/extension-stores-api) does this: its listing and release-notes dry runs list the unsupported tags before anything is sent. The live listing (`GET /api/v5/addons/addon/<id>/`, no `lang`) shows which locales currently carry text — 29 for the summary on 2026-10-01.

### Where the mapping lives

A single exported table in the new script, shaped like the one in [`scripts/locales.mjs`](../scripts/locales.mjs) — the project's established pattern of one source table per generated thing:

```js
/** store-descriptions.md heading tag -> AMO locale key, or null to skip. */
const AMO_LOCALE = {
  en: 'en-US',
  es: 'es-ES',
  no: 'nb-NO',
  sv: 'sv-SE',
  // Not in AMO's production list; sending them is a silent no-op.
  am: null, ar: null, bg: null, bn: null, ca: null, da: null, 'en-AU': null,
  'es-419': null, et: null, fil: null, gu: null, hi: null, id: null, kn: null,
  lt: null, lv: null, ml: null, mr: null, ms: null, sw: null, ta: null,
  te: null, th: null,
  // ...identity for the rest
};
```

`null` means "this translation exists for Opera or Chrome but AMO cannot take it" — skipped with a printed note, never silently dropped.

## Parsing the descriptions

[`store-descriptions.md`](store-descriptions.md) is already machine-readable by accident of its own conventions, and [`scripts/set-description.mjs`](../scripts/set-description.mjs) already proves the shape can be matched by regex. A reader needs to:

1. Match each `^## \`(tag)\` — (name)$` heading.
2. Take the single ` ```text ` fence that follows as the body.
3. Ignore the `_Translated from the English description._` line — it sits outside the fence precisely so it never reaches a store. **The reader must preserve that boundary**: fence contents only.

Export the parser as a function so it is testable with [vitest](../vitest.config.ts) against the real file, the way `setDescription` already is.

Summaries are a separate problem. `store-descriptions.md` holds **descriptions only**; the per-language summary exists for `en` and `tr` alone, in [`amo-submission.md`](amo-submission.md). Options:

- **Recommended:** add a `## Summaries` section to `store-descriptions.md`, one fence per tag, filled in over time. `PATCH` only the locales that have one. AMO falls back to `default_locale` for the rest, which is correct behaviour, not a gap.
- Rejected: deriving a summary from the description's first paragraph. It would exceed 250 characters and read badly.

### `chrome://` must become `about:` for AMO

The descriptions in [`store-descriptions.md`](store-descriptions.md) were written for the Chromium stores, so most of them name Chromium's own pages. AMO's listing must not: on Firefox the equivalent pages are `about:` and the add-ons site, and `chrome://` is both wrong and confusing to a Firefox user reading the listing. [`amo-submission.md`](amo-submission.md) already says `about:` in its English and Turkish text; the per-language file does not follow.

Measured against the current file:

| Wording                                | Sections | Note                                                                 |
| -------------------------------------- | -------- | -------------------------------------------------------------------- |
| `chrome://` + "Web Store"              | 55       | **Must be rewritten before reaching AMO**                            |
| `about:` + add-ons site                | 13       | Already correct — `dsb en-CA es-AR es-CL es-MX fur fy-NL hsb ia ka kab nn-NO sq` |

No section mixes the two, so the split is clean. The 13 already-correct ones are the AMO-only languages, which had no Chrome listing to be written for.

Note that `en-US` and `tr` are in the 55, i.e. the two listings that matter most are the wrong ones today.

Two ways to fix it, and the choice matters:

- **Rejected: edit the file to say `about:`.** It is one file serving four stores. Changing it corrects AMO and breaks Chrome, Edge and Opera, which is how [`opera-submission.md`](opera-submission.md) already ended up documenting a manual `chrome://` → `opera://` substitution by hand.
- **Recommended: substitute at publish time.** The script rewrites the text on its way to AMO, leaving the source file as the Chromium-facing copy it already is. Opera's documented substitution then becomes the same mechanism rather than a note telling a human to do it.

So the transform belongs next to the parser, as a per-store table:

```js
/** Browser-page wording, per store. Source file carries the Chromium form. */
const SCHEME = {
  amo: [
    [/chrome:\/\//g, 'about:'],
    // "Web Store" -> the add-ons site, per language. Needs a translated term,
    // so this cannot be one regex - see below.
  ],
  opera: [[/chrome:\/\//g, 'opera://']],
};
```

> [!WARNING]
> `chrome://` → `about:` is a safe global replace; **the store name is not**. "Web Store" appears in 16 sections in English, but the other 39 translate it ("la Web Store", "веб магазина", "ウェブストア"), and AMO's equivalent is the add-ons site, whose name also translates. A blind regex would leave a Firefox listing advertising Chrome's store in Turkish.
>
> Two options, neither free: add a second fence per section carrying the AMO-specific sentence (explicit, verbose, and the 13 AMO-only sections show what it looks like), or a per-language term table mapping each translation of "Web Store" to its add-ons-site equivalent. The first is more work up front and cannot silently produce wrong text, so prefer it.
>
> Until one of them exists, **`listing` must not publish the 31 Chromium-worded sections that reach AMO** (the other 24 of the 55 never reach it: 23 unsupported locales plus `en`). Ship the 13 correct ones plus a rewritten `en-US` and `tr` first; that is the bulk of the real audience. Gate the rest behind an explicit flag so a run cannot quietly publish text naming the wrong browser.

This changes the step order below: the substitution problem is now the first thing `listing --dry-run` has to show, because a dry run that prints `chrome://` in a Firefox listing body is the one error this whole document exists to prevent.

### Field limits and format

- **Summary:** 250 characters, hard limit. Validate before sending; a rejected `PATCH` is one round trip wasted and the error is not always clear about which locale failed.
- **Description:** accepts some Markdown. The existing text is plain with `•` bullets and blank-line paragraphs; AMO renders that acceptably today. Do not "improve" it as part of this work — a formatting change and an automation change in one commit means a rendering regression has two possible causes.
- Translated fields are **merge, not replace**: locales omitted from a `PATCH` are left alone; sending `null` for a locale deletes that translation. So a partial run is safe, and a locale being removed from the repo does not silently remove it from the listing.

## Proposed shape

One new script, mirroring the existing `scripts/*.mjs` conventions — a file-header comment explaining why it exists, `--help`, no runtime dependencies:

```text
scripts/amo.mjs
```

Subcommands, smallest useful first:

| Command                     | Does                                                                          |
| --------------------------- | ----------------------------------------------------------------------------- |
| `amo.mjs whoami`            | Signs a JWT, hits `GET /accounts/profile/`. Proves credentials work.          |
| `amo.mjs listing --dry-run` | Parses the descriptions, resolves locales, prints the `PATCH` body. No write. |
| `amo.mjs listing`           | `PATCH`es summary + description for every mapped locale.                      |
| `amo.mjs upload`            | Uploads `dist/firefox-mv2-<version>.zip`, polls until validated, reports.     |
| `amo.mjs version`           | Creates the version: upload uuid, license, notes, source archive.             |
| `amo.mjs release`           | `upload` then `version` then `listing`, in that order.                        |

Ordering in `release` matters: the version is created first, so if the listing `PATCH` fails the version still exists and the listing can be retried independently. The reverse would leave a listing describing a version that was never submitted.

Corresponding `package.json` scripts, matching the existing naming (`describe`, `locales`, `promo`):

```json
"amo": "node scripts/amo.mjs",
"amo:listing": "node scripts/amo.mjs listing",
"amo:release": "node scripts/amo.mjs release"
```

### Fixed values the script needs

From [`amo-submission.md`](amo-submission.md) and [`publishing.md`](publishing.md), these are already decided and should be constants in the script, not prompts:

| Field            | Value                                                                      |
| ---------------- | -------------------------------------------------------------------------- |
| Add-on id        | the slug or GUID — read it from the live API on first run and hard-code    |
| Upload file      | `dist/firefox-mv2-<version>.zip`, version from `package.json`              |
| Channel          | `listed`                                                                   |
| License          | AGPL-3.0-only — the slug AMO uses, to be read from `GET /addons/licenses/` |
| Category         | `photos-music-videos` (AMO's extension list has no audio-only category)    |
| Source           | `dist/source-<version>.zip` from `pnpm run source`                         |
| `approval_notes` | the **compact** reviewer note — the field truncates long input silently    |
| `release_notes`  | the version-notes block, `{ "en-US": ... }`                                |

> [!NOTE]
> `approval_notes` via the API may not truncate the way the web form does, but the compact note is the safe choice until tested. Test it once with the full note against staging and record the outcome here.

## Build or buy

`web-ext sign` can already create and update listings through API v5, taking metadata as JSON via `--amo-metadata`. Considered and rejected as the primary path:

- It signs and distributes; the listing metadata is a side feature. The interesting work here — reading 71 translations out of a Markdown file and mapping their tags onto AMO's vocabulary — it does not do, so `--amo-metadata` would still need generating. That generator is most of the script.
- It would be the project's first runtime-adjacent dependency on a large package, in a repo that hand-writes its own zip and icons rather than depend on libraries.

`pnpm dlx web-ext sign` stays available as a fallback if the hand-rolled upload path proves fragile, and is worth mentioning in the script's header comment so the next person knows it was a considered choice.

## Testing without publishing something

Three layers, in order of how much they protect:

1. **Pure functions under vitest** — the description parser and the locale mapper, against the real `store-descriptions.md`. Catches the whole class of bug where a heading changes and translations silently stop being found. No network, runs in CI today.
2. **`--dry-run` everywhere** — print the exact request body and exit. Should be the default for `listing` until it has been run successfully once.
3. **Staging** — `https://addons.allizom.org/api/v5/`, or `addons-dev.allizom.org`. Production credentials **do not work** there; a separate account and separate API keys are needed. Make the base URL an environment variable (`AMO_API_BASE`, defaulting to production) so the same script hits either.

> [!IMPORTANT]
> The first real `listing` run should target a single locale — `--locale=tr` — before running all 44. A mistake in the mapping that overwrites 44 descriptions with the wrong text is recoverable only by re-running with correct data, and the listing is public in the meantime.

## CI

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) already runs typecheck, tests, lint, `addons-linter` on both Firefox targets, and verifies generated assets are current. It should stay untouched: it runs on every push and must never need secrets.

Publishing belongs in a separate, tag-triggered workflow:

```yaml
on:
  push:
    tags: ['v*']
```

Steps: build, `pnpm run source`, then `amo.mjs release`, with `AMO_JWT_ISSUER` / `AMO_JWT_SECRET` from repository secrets. Guard it with a GitHub Environment requiring manual approval — a mistyped tag should not publish.

Also worth adding, and cheap: a CI check that every `## \`tag\``heading in`store-descriptions.md`resolves through the locale map. That turns "AMO rejected locale`es-419`" from a failed release into a failed pull request.

## Order of work

Each step ends somewhere useful, and nothing writes to production until step 5.

1. `scripts/amo.mjs` with the JWT signer and `whoami`. Confirms the credentials and the token lifetime rule. ~80 lines.
2. The description parser + locale map, exported, with vitest tests against the real file. No network.
3. `listing --dry-run`. Prints the body. Review the resolved locale list by eye — this is the step that catches mapping errors. **Grep the printed body for `chrome://` and for "Web Store": both must be absent, in every language.**
4. Read the live add-on: `GET /addons/addon/<id>/`, and diff its existing translations against what step 3 would send. Reconcile the locale table against reality.
5. `listing --locale=tr` for real. One locale. Verify on the site — including that it says `about:`, not `chrome://`.
6. `listing` for the 13 already-correct sections plus a rewritten `en-US` and `tr`. The remaining 29 AMO locales wait on the "Web Store" term problem above, behind an explicit flag.
7. `upload` + `version`, tested against staging first if a staging account is available; otherwise on the next real release, with the manual path ready as a fallback.
8. The tag-triggered workflow, gated on manual approval.
9. Add the `store-descriptions.md` heading check to `ci.yml`.

Steps 1–3 need no credentials beyond `whoami` and deliver the part that is actually painful today. If the work stops after step 6, the release is already most of the way automated.

## Open questions

- **Summaries for the other 64 languages.** Only `en` and `tr` have one today. Needed for a complete listing; the descriptions are already translated, so this is the same job again at 250 characters. Not a blocker for descriptions.
- **The add-on's numeric id or slug.** Read it from the API on first run and record it here.
- **The AMO license slug for AGPL-3.0-only.** `GET /api/v5/addons/licenses/` — confirm the exact slug rather than guessing.
- **Whether a staging account is worth creating.** It costs an account and a separate key pair, and buys a safe rehearsal of `upload` + `version`. Probably yes before step 7.
- **Rate limits.** Undocumented. 44 sequential `PATCH`es may hit one. Send them as a single `PATCH` with all locales in one translated-field object — one request, not 44 — which sidesteps the question entirely and is the documented format anyway.
